# Showy — персональні сторінки

> **Картка сервісу (запланований).** Читати разом із `docs/context/00-overview-uk.md`. **Стан на:** 2027-01-14. Коду ще немає: це задум і відкриті питання. Джерело правди — `docs/decisions.md`, `docs/backlog.md`.

## 1. Призначення

Публічне обличчя компанії й людей: лендінги, візитівки, корпоративні сторінки.

- **Стан:** ⏳ у планах.

## 2. Задум

| Що | Тариф |
|---|---|
| **Візитівки з блоків** — для компанії й окремо для кожного профілю | Free |
| **Лендінг компанії** з готових блоків, без власного коду | Free |
| Лендінг із **власним кодом усередині сайту** | Team |
| **Корпоративні сторінки з власним кодом** — компанія розгортає власні сервіси | Business |

Обмеження коду на Free потрібне, щоб розділ не використовували для розгортання застосунків.

Зразок підходу до візитівок — інший сервіс власниці (блочний конструктор).

## 3. Очікувані зв'язки

| Сервіс | Зв'язок |
|---|---|
| **Wika** | публічна база знань — споріднена можливість (читання без входу) |
| **Questa** | форма на лендінгу |
| **Obriy** | корпоративні сторінки з кодом близькі до власних додатків: межу між сервісами треба визначити |
| **Vault** | зображення й файли сторінок |

## 4. Відкриті питання

- Публічні сторінки — це доступ без входу → погодження; окремий домен для чужого коду, щоб він не мав доступу до сеансу людини.
- Власний домен компанії.
- Позначка «Зроблено в …» на Free.
- Чим «корпоративна сторінка з кодом» відрізняється від «власного додатка» в Obriy.

## Спільні правила для будь-якого нового сервісу

- Це розділ платформи: спільні акаунти, workspace, ролі, підрозділи, гості, сховище, пошук, сповіщення.
- Дані — у таблицях із `workspace_id` і правилами доступу в базі; дві міграції (центральна й командна) плюс перенесення між базами.
- Нові таблиці й правила доступу — окреме погодження власниці до коду.
- Плитка сервісу вже є на стартовій сторінці й лендінгу з позначкою «Скоро» (`src/lib/services.ts`).
- Жодних назв і логотипів сторонніх продуктів.
