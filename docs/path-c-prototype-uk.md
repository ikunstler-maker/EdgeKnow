# Шлях В: звіт прототипу і план етапу 1

> Крок 1.1 дорожньої карти (`docs/roadmap-uk.md`). Код прототипу — `prototype/path-c/`, запуск — GitHub Actions «Prototype path C». На робочий сайт не впливає.

## Питання

Людина входить через центральний сайт EdgeKnow, а дані її команди лежать у Supabase **самої команди**. Чи може браузер працювати з базою команди напряму так, щоб:
- це було безпечно;
- центральний хостинг майже не навантажувався;
- команді не треба було налаштовувати вхід Google?

## Що перевірено

Два окремі Supabase («команда А» і «команда Б»), кожен зі своїм ключем підпису. Скрипт грає роль центрального сервісу.

**Результат: 15 з 15 перевірок пройшли.**

| | Перевірка |
|---|---|
| ✅ | Ключі доступу до баз команд центральний сервіс зберігає лише в зашифрованому вигляді |
| ✅ | У кожної команди свій ключ підпису |
| ✅ | Структуру бази (міграції) встановлено в базу кожної команди |
| ✅ | Недоступна база команди показується як помилка, а інші команди однаково оновлюються |
| ✅ | Повторний запуск оновлення нічого не змінює і не дублює |
| ✅ | **База команди приймає «перепустку» (токен), видану центральним сервісом** |
| ✅ | База бачить, хто саме робить запит, тож правила доступу (RLS) працюють як зараз |
| ✅ | Кожен читає лише те, що йому дозволяють правила |
| ✅ | Записати щось від імені іншої людини неможливо |
| ✅ | Перепустка команди А нічого не відкриває в команді Б |
| ✅ | Перепустку, підписану будь-яким іншим ключем, база відхиляє |
| ✅ | Прострочену перепустку база відхиляє |
| ✅ | Без перепустки нічого не прочитати |
| ✅ | Зупинену базу команди видно за кілька секунд |
| ✅ | Інші команди при цьому працюють далі |

## Висновки

1. **Обираємо спосіб «а»: база команди довіряє перепустці від центрального сервісу.** Механізм працює.
   - Браузер ходить у базу команди напряму, тож ваш хостинг лише видає перепустку раз на кілька хвилин.
   - Права перевіряє сама база, тими самими правилами, що й зараз.
   - Налаштовувати вхід Google команді не потрібно.
2. **Важливий висновок про безпеку.** Хто має ключ підпису команди, той може видати собі перепустку «адміністратора» і бачити всю базу команди. Прототип це підтвердив.
   - Тому ключі команд зберігаємо так само суворо, як зараз доступ до Google Drive: зашифрованими, лише на сервері, ніколи в браузері, з можливістю заміни.
   - Це треба чесно написати в умовах використання: команда довіряє сервісу доступ до своєї бази.
3. **Спосіб «б» (усе через ваш сервер) теж працює, але гірший.**
   - Сервер бачить усе, тож права перевірялися б лише нашим кодом, а не базою.
   - Увесь трафік ішов би через ваш хостинг.
   - Лишаємо його тільки як запасний.
4. **Людей у базі команди немає.** Акаунти зберігаються в центральному сервісі. База команди лише довіряє тому, кого назвала перепустка. Структуру таблиць треба буде трохи змінити: прибрати прямі посилання на таблицю акаунтів.

## Що прототип не перевірив

Мережа цієї сесії не пускає на supabase.com, тому дві речі про **хмарний** Supabase я не змогла перевірити:

1. Як команда передає ключ підпису у свій хмарний проєкт: імпортом готового ключа в налаштуваннях чи якось інакше. Від цього залежить, скільки кроків буде в майстрі підключення.
2. Чи можна замість ручного копіювання зробити кнопку «Підключити Supabase» (вхід через Supabase). Сервіс сам створив би проєкт команди, встановив структуру бази й ключ. Тоді підключення займало б 2 кліки замість 15 хвилин.

Щоб перевірити ці пункти, треба дозволити сесії доступ до `supabase.com` і `api.supabase.com`. Інструкція — у відповіді в чаті.

## План етапу 1 (на ваш OK)

Кожен крок закінчується перевіркою «Готово, коли…» і автоматичними тестами.

| Крок | Що робимо | Готово, коли | Орієнтовно |
|---|---|---|---|
| 1.2 | Перевірка хмарного Supabase: ключ підпису, вхід через Supabase (OAuth), ліміти безкоштовного тарифу | Відомо точні кроки майстра; на тестовому хмарному проєкті працює перепустка | 1–2 дні |
| 1.3 | Розділити базу на дві частини: **центральну** (акаунти, список workspace, зашифровані ключі, тарифи, статистика) і **командну** (сторінки, доступи, коментарі, файли, згадки, статистика профілю). Плюс автоматичне оновлення баз усіх команд | Тести безпеки проходять для обох частин; оновлення доходить до кожної команди рівно один раз | 1–2 тижні |
| 1.4 | Видача перепусток і робота сайту з базою команди | Сторінки, коментарі й пошук працюють з базою команди; запити до центрального сервера — лише за перепусткою | 1–2 тижні |
| 1.5 | Майстер підключення: покрокові підказки, перевірка, зрозумілі помилки, стан бази («заснула», переповнена, ключ відкликано) | Новачок підключає свій Supabase за ≤ 15 хвилин без сторонньої допомоги | 1 тиждень |
| 1.6 | Файли: Google Drive або сховище Supabase команди; резервні копії на Drive | Зображення й обкладинки завантажуються і показуються з ресурсів команди | 1 тиждень |
| 1.7 | Перенесення нашого поточного workspace у нову схему, з планом відкату | Усі сторінки, коментарі, доступи й файли на місці; відкат перевірено | 3–5 днів |
| 1.8 | Тести безпеки двох команд у CI (як у прототипі), перевірка, що центральна база не містить вмісту сторінок | Усі перевірки зелені | разом з кроками вище |

**Разом:** приблизно 6–9 тижнів.

**Під час переходу:** робочий сайт працює як зараз. Перемикання на нову схему відбудеться одним кроком 1.7, з резервною копією і можливістю відкату.
