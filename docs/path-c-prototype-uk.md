# Шлях В: звіт прототипу і план етапу 1

> Крок 1.1 дорожньої карти (`docs/roadmap-uk.md`). Код прототипу — `prototype/path-c/`, запуск — GitHub Actions «Prototype path C». На робочий сайт не впливає.

## Питання

Людина входить через центральний сайт EdgeKnow, а дані її команди лежать у Supabase **самої команди**. Чи може браузер працювати з базою команди напряму так, щоб:
- це було безпечно;
- центральний хостинг майже не навантажувався;
- команді не треба було налаштовувати вхід Google?

## Що перевірено

Два окремі Supabase («команда А» і «команда Б»), кожен зі своїм ключем підпису. Скрипт грає роль центрального сервісу.

**Результат: 15 з 15 перевірок пройшли.**

| | Перевірка |
|---|---|
| ✅ | Ключі доступу до баз команд центральний сервіс зберігає лише в зашифрованому вигляді |
| ✅ | У кожної команди свій ключ підпису |
| ✅ | Структуру бази (міграції) встановлено в базу кожної команди |
| ✅ | Недоступна база команди показується як помилка, а інші команди однаково оновлюються |
| ✅ | Повторний запуск оновлення нічого не змінює і не дублює |
| ✅ | **База команди приймає «перепустку» (токен), видану центральним сервісом** |
| ✅ | База бачить, хто саме робить запит, тож правила доступу (RLS) працюють як зараз |
| ✅ | Кожен читає лише те, що йому дозволяють правила |
| ✅ | Записати щось від імені іншої людини неможливо |
| ✅ | Перепустка команди А нічого не відкриває в команді Б |
| ✅ | Перепустку, підписану будь-яким іншим ключем, база відхиляє |
| ✅ | Прострочену перепустку база відхиляє |
| ✅ | Без перепустки нічого не прочитати |
| ✅ | Зупинену базу команди видно за кілька секунд |
| ✅ | Інші команди при цьому працюють далі |

## Висновки

1. **Обираємо спосіб «а»: база команди довіряє перепустці від центрального сервісу.** Механізм працює. Для хмари він буде у вигляді Custom OIDC, див. крок 1.2.
   - Браузер ходить у базу команди напряму, тож ваш хостинг лише видає перепустку раз на кілька хвилин.
   - Права перевіряє сама база, тими самими правилами, що й зараз.
   - Налаштовувати вхід Google команді не потрібно.
2. **Важливий висновок про безпеку.** Хто має ключ підпису, той може видати собі перепустку «адміністратора» і бачити всю базу. Прототип це підтвердив, і саме від цього захищає перевірка «лише звичайний користувач» (крок 1.2).
   - Тому ключі команд зберігаємо так само суворо, як зараз доступ до Google Drive: зашифрованими, лише на сервері, ніколи в браузері, з можливістю заміни.
   - Це треба чесно написати в умовах використання: команда довіряє сервісу доступ до своєї бази.
3. **Спосіб «б» (усе через ваш сервер) теж працює, але гірший.**
   - Сервер бачить усе, тож права перевірялися б лише нашим кодом, а не базою.
   - Увесь трафік ішов би через ваш хостинг.
   - Лишаємо його тільки як запасний.
4. **Людей у базі команди немає.** Акаунти зберігаються в центральному сервісі. База команди лише довіряє тому, кого назвала перепустка. Структуру таблиць треба буде трохи змінити: прибрати прямі посилання на таблицю акаунтів.

## Крок 1.2: що вміє хмарний Supabase (перевірено за офіційною документацією, 2026-11-09)

1. **Supabase офіційно довіряє «чужому» входу (Custom OIDC).** У проєкті команди додається один рядок: адреса нашого сервісу входу («issuer URL»). Після цього база команди приймає перепустки, які видає EdgeKnow, і бачить, хто прийшов, як у прототипі. Це краще за варіант із прототипу:
   - **приватний ключ нікуди не передається.** Він лишається тільки в нас, команді нічого зберігати не треба;
   - ключ можна змінити в нас, і всі команди підхоплять зміну самі (протягом 30 хвилин);
   - ліміт безкоштовного тарифу — **50 000 активних людей на місяць** на проєкт команди. Для вікі з тисячами читачів цього досить.
2. **Кнопка «Підключити Supabase» можлива.** Supabase має офіційні OAuth-застосунки й Management API. Після згоди людини наш сервіс може сам:
   - створити проєкт у її Supabase;
   - додати наш вхід (Custom OIDC);
   - встановити й оновлювати структуру бази;
   - отримати ключі;
   - перевіряти стан проєкту;
   - **«розбудити» базу, яка заснула** після тижня без активності.

   Доступи у OAuth-застосунку обмежені за видами дій (база, ключі, вхід, проєкти). Підключення для команди — кілька кліків замість 15 хвилин копіювання.
3. **Обмеження безкоштовного Supabase:** 500 МБ бази, 1 ГБ файлів, 5 ГБ трафіку на місяць, не більше 2 активних безкоштовних проєктів на організацію, пауза після тижня без активності.

**Нове щодо безпеки.** Тепер один наш ключ підпису діє для всіх команд. Тому:
- у базу кожної команди ставимо захист: перепустка від EdgeKnow може бути **лише звичайним користувачем** і ніколи не «адміністратором», навіть якщо ключ хтось украде;
- доступ OAuth до проєктів команд (так званий «refresh token») зберігаємо зашифрованим, як доступ до Drive.

**Ще не перевірено наживо.** Це перевіримо на тестовому хмарному проєкті:
- чи потрібна перевірка OAuth-застосунку з боку Supabase, перш ніж ним зможуть користуватися інші люди;
- чи працює захист «лише звичайний користувач» на хмарі так само, як локально.
